# Заключение: данные прибора/точки учёта, необходимые для построения дерева баланса

## 0. Источники и метод

Первая версия этого документа опиралась только на открытые описания продуктов (сайты
вендоров, отраслевые статьи) — прямой доступ к работающим интерфейсам систем в этой среде
отсутствует. Позднее пользователь предоставил два первичных источника, которые заменяют
предположения на подтверждённые факты:

1. **«Пирамида 2.0 — Руководство пользователя. Личный кабинет потребителя»** (34 стр.,
   скриншоты интерфейса, включая раздел **4.4.3 «Баланс электроэнергии»** — ключевой для
   данной задачи);
2. **«Альфа ЦЕНТР на базе ORACLE — Выгрузка данных в формате csv + мониторинг»** (7 стр.,
   скриншоты интерфейса расчётных групп и структуры выгружаемых файлов).

Ниже раздел 1 обновлён по этим первичным источникам; раздел про АИС OMNI-US оставлен как
вторичный (по открытым описаниям — прямых скриншотов не предоставлено). Раздел 3 фиксирует,
какие изменения по итогам этого разбора уже внесены в код `src/EnergyBalance.Domain` и

## 1. Подтверждённые данные по трём системам

### 1.1. ПО «Пирамида 2.0» (личный кабинет потребителя) — первичный источник

**Паспорт точки учёта / прибора учёта** (раздел «Точки учёта» → «Описание»), дословный
список атрибутов из интерфейса:

*Прибор учёта:* Тип (модель), Серийный номер, **Номер пломбы**, **Класс точности**, Дата
последней поверки, Дата следующей поверки, Дата установки, Дата получения данных.

*Точка учёта:* Тип (в классификации системы), Адрес, Тариф, **Состояние нагрузки** (реле:
Включено/Отключено/Не определено), **Лимит мощности, кВт**, Ктт, Ктн, **Максимальная
заявленная мощность, кВт**, **Максимальный коэффициент реактивной мощности tg(φ)**,
Описание места установки, Адрес энергопринимающего устройства.

**Измеряемые величины** (разделы «Электроэнергия» и «Профиль»):
- Энергия **A+** (приём) и **A-** (выдача) — оба направления как равноправные параметры,
  по тарифным зонам («Дневная», «Ночная», «Общее потребление»);
- Энергия **P+** и **P-** (реактивная, оба направления);
- Профиль — «Энергия за 30 минут / за 1 час», «Мощность за 30 минут / за 1 час»;
- Каждое значение несёт метаданные: **метка времени, время фактического получения, тип
  источника данных** (прибор учёта / ручной ввод / расчётная формула / импортированные
  данные) **и список статусов достоверности**.

**Параметры сети** (векторная диаграмма, по фазам): активная/реактивная/полная мощность,
напряжение, ток, cos(φ), tg(φ), угол между векторами U/I, частота сети, угол между
фазными напряжениями, линейное напряжение.

**Раздел 4.4.2 «Нарушения»** — автоматический контроль 5 типов событий: нарушение
целостности корпуса, магнитное воздействие, нарушение tg(φ), нарушение уровня напряжения,
нарушение уровня частоты; статус объекта — «Норма»/«Нарушение».

**Раздел 4.4.3 «Баланс электроэнергии» — ключевой для данной задачи.** Дословно:
«Балансируемый объект формируется в случае наличия вводного прибора учёта и распределения
электроэнергии по внутренним точкам учёта абонента». Форма представления:

| Поле | Значение |
|---|---|
| **Направление перетока** | «Исключено» / «Принято» / «Отдано» / «Собственные нужды», с индикацией *фактического* направления перетока (система сверяет заданную роль с реально измеренным направлением) |
| Принято | сумма по принятой электроэнергии |
| Отдано | сумма по отданной электроэнергии |
| Собственные нужды | сумма по энергии, затраченной на собственные нужды объекта |
| Небаланс | Принято − Отдано − Собственные нужды (проверено на примере из документа: 17668,721 − 17662,188 − 0 = 6,533 — сходится) |
| Небаланс, % | небаланс в относительных величинах |

Балансируемые объекты образуют **дерево** (в примере: ТСЖ → «Ввод 1» → «д.5» → квартиры),
то есть балансовая группа может включать вложенные группы — ровно та структура, которую
уже реализует `BalanceGroup.ParentGroupId` в нашей модели.

Смежные разделы **4.4.4 «Максимальная мощность»** и **4.4.5 «Фактическая и резервируемая
мощности»** показывают, что параллельно энергетическому балансу система ведёт отдельный
**мощностной баланс** (факт/резерв/максимум мощности против «Максимальной заявленной
мощности» из паспорта точки, с индикацией превышения) — важная, но самостоятельная
функция, не смешиваемая с энергетическим балансом.

### 1.2. АСКУЭ АльфаЦЕНТР — первичный источник

Документ описывает модуль выгрузки «Профили групп за сутки» и экранную форму управления
расчётными группами. Подтверждён **двухуровневый** состав расчётных групп («1-го уровня» и
«2-го уровня» на скриншоте формы) и следующая структура описания каждой группы в выгрузке:

- тип объекта (Подстанция/Гидроэлектростанция/...), название, код типа объекта, номер
  объекта, номер группы;
- **«гр.коммент»** — свободный комментарий, описывающий состав/назначение группы (например,
  «поступление по классам напряжения», «Отпуск в сети других АО», «Баланс», «Производственные
  нужды», «Тяга») — то есть комментарий фактически кодирует роль/тип группы;
- **«АЗ/РЭ»** — единица и направление величины (например, «А+ кВтч») — снова подтверждение
  разделения по направлению энергии;
- **«детализац.»** — класс/уровень напряжения, к которому относится группа (35 кВ, 110 кВ,
  «не детализировано») — атрибут группы, не точки, но важный для агрегации по уровням сети;
- для каждого получасового интервала на группу выводится **4 значения: Расход, Статус,
  «должно быть» (ожидаемое количество первичных записей за интервал), «есть реально в базе»**
  — то есть встроенный количественный контроль полноты исходных данных на уровне
  каждого расчётного интервала, а не только сводный признак по прибору.
- отдельная опция «Выводить данные с учётом процентов потерь (указаны на фидерах)» —
  подтверждает, что норматив потерь в этой системе хранится как атрибут **фидера**, а не
  обязательно балансовой группы.

### 1.3. АИС OMNI-US (вторичный источник — открытые описания)

Оценка не изменилась: система в первую очередь биллинговая (лицевой счёт/договор), точка
учёта там в первую очередь связана с абонентом, а не с топологией сети — прямых скриншотов
структуры балансовых данных не предоставлено.

## 2. Итоговый вывод

Оба первичных источника независимо подтверждают одну и ту же модель, которая с самого
начала была заложена в EnergyBalance, и одновременно указывают на три конкретных пробела,
которые были обнаружены на первой итерации этого анализа (см. историю документа) и **устранены
по итогам разбора первичных источников** (раздел 3):

1. энергия должна учитываться в обоих направлениях (**A+/A-**, **P+/P-**), а не только как
   однонаправленный приход;
2. роль точки учёта в балансовой группе — не бинарная (приход/расход), а как минимум
   **четырёхзначная**: Принято / Отдано / Собственные нужды / Исключено;
3. система должна отдельно учитывать классификационные и метрологические атрибуты точки
   (класс точности, максимальная заявленная мощность, максимальный tg φ, номер пломбы),
   не входящие непосредственно в формулу баланса, но обязательные для паспорта точки и
   контроля превышений.

## 3. Что изменено в модели EnergyBalance по итогам разбора

| # | Изменение | Статус |
|---|---|---|
| 1 | `BalanceMemberRole`: добавлены `OwnNeeds` («Собственные нужды») и `Excluded` («Исключено») к существующим `Supply`/`Consumption` | ✅ внесено |
| 2 | `Reading`/`LoadProfileReading`: добавлена энергия «выдача» (А-) по тарифам и раздельные Р+/Р- вместо одного суммарного значения реактивной энергии | ✅ внесено |
| 3 | `BalanceCalculationResult`: добавлено поле `OwnNeedsEnergyKwh`; формула фактических потерь скорректирована — `ActualLossKwh = Отпуск − Потребление − СобственныеНужды` (проверено на числовом примере из «Пирамида 2.0», см. 1.1) | ✅ внесено |
| 4 | `BalanceCalculator`: обработка роли `OwnNeeds` (отдельная сумма, не потеря) и `Excluded` (точка полностью исключается из статистики) | ✅ внесено |
| 5 | `BalanceCalculationOrchestrator`: суммарная энергия точки учёта за период теперь считается как **нетто** (А+ минус А-) — корректно для точек с двусторонним перетоком | ✅ внесено |
| 6 | `MeteringPoint`: добавлены класс точности ТТ/ТН, максимальная заявленная мощность, максимальный tg φ, текущий лимит мощности | ✅ внесено |
| 7 | `Meter`: добавлен номер поверительной пломбы | ✅ внесено |
| 8 | Все драйверы сбора данных (`MercuryProtocolClient`, `SiriusModbusClient`, `MasterOpcClient`) и карты тегов/регистров обновлены под новую раскладку A+/A-/P+/P- | ✅ внесено |
| 9 | Мощностной баланс (факт/резерв/максимум против заявленной мощности, см. 1.1) как отдельная от энергетического баланса функция | ⏳ не реализовано — самостоятельная задача, требует отдельного расчётного модуля по аналогии с `BalanceCalculator`, но на профиле мощности, а не энергии |
| 10 | Поинтервальный контроль полноты данных «должно быть / есть реально» (см. 1.2), а не только признак «есть проблемы» на весь период | ⏳ не реализовано — потребует хранения ожидаемого количества интервалов на приборе/группе и посчитанного факта |
| 11 | Понятие ГТП (группа точек поставки, термин 442-ПП) как отдельный тип балансовой группы верхнего уровня | ⏳ остаётся открытой рекомендацией из первой версии документа |

Пункты 9–11 не реализованы в этой итерации — предлагаю реализовать по приоритету, который
укажете; технически они не требуют архитектурных изменений, только дополнение модели и
расчётного слоя по уже заданному образцу.
